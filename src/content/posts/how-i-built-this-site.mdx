## CSS Variables That Commit Identity Fraud

Here's a fun one. In my CSS, I have a variable called `--color-neon-cyan`. Sounds straightforward, right? Here's what it actually is:

```css

```

That's orange. Bright, aggressive, _definitely not cyan_ orange.

I named it cyan because I originally planned for a cyberpunk blue theme. Then I changed my mind. Did I rename the variable? Did I go through 40+ files updating references? No. No I did not.

### useSyncExternalStore for What Now?

In my baby countdown component: yes, there's a baby countdown component, we'll get to that. I use `useSyncExternalStore` to check if the component has mounted.

For the uninitiated: `useSyncExternalStore` is a React hook designed for subscribing to external data sources like Redux stores or browser APIs. I'm using it to return `true` after hydration.

A simple `useEffect` would have done the same thing, since it only runs client-side anyway. But where's the fun in that?

It's like using a sledgehammer to hang a picture frame. The picture is up. The wall has structural damage. But it _works_.

### Strategy Pattern for a Baby Countdown

Speaking of that baby countdown, let me tell you about the time I decided it needed "enterprise-grade architecture."

The component has four states: loading, countdown, past due, and born. A normal person would write this:

```tsx
switch (state) {
  case 'loading':
    return <Loading />;
  case 'born':
    return <Born />;
  case 'pastDue':
    return <PastDue />;
  case 'countdown':
    return <Countdown />;
}
```

Simple. Readable. Boring.

Instead, I implemented the **Strategy Pattern**. Each state gets its own strategy object with an icon, title, `getProgress` function, and `renderContent` function. The component just looks up the current strategy and delegates everything.

```tsx
const countdownStrategies: Record<CountdownState, CountdownStrategy> = {
  loading: {
    icon: '👶',
    title: 'LOADING NEW HUMAN...',
    getProgress: () => 0,
    renderContent: () => <div>Calculating...</div>,
  },
  born: {
    icon: '🎉',
    title: 'NEW HUMAN DEPLOYED TO PRODUCTION',
    getProgress: () => 100,
    renderContent: () => <p>Expect bugs. Sleep schedule: undefined</p>,
  },
  // ... you get the idea
};
```

Is this more maintainable? Arguably. Is it more extensible? Sure, if I plan on having more babies just to add states. Is it necessary for a component that will be relevant for approximately 9 months?

_Absolutely not._

But the code has a comment that says: "Because every baby countdown deserves enterprise-grade architecture."

At least I'm self-aware.

## The Actual Truth

Look, beneath all the jokes, there's something genuinely impressive here, and it's not me.

Two days. Full responsive design. Blog with MDX. Contact form. CI/CD. SEO optimization. Animations. Easter eggs. _This blog post about the blog._

That's what's possible now with AI assistance. It's wild. It's a little scary. It made me feel simultaneously empowered and obsolete, sometimes in the same commit.

But here's the thing: the AI didn't write the jokes. It didn't know that `--color-neon-cyan` being orange is funny. It didn't understand why a fake `.zshrc` with `alias yolo="git push --force"` would resonate with developers.

The code is collaborative. The chaos is all me.

And I think that's worth something. Maybe not a job. But something.
